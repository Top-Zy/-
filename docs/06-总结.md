# 毕业设计总结

## 1 项目完成情况

本次毕业设计围绕“武陵山区果园管理系统的设计与实现”展开，完成了从需求调研、系统设计、数据库设计、前端开发、后台开发到测试与文档撰写的完整过程。最终交付一个可在浏览器中直接运行的多页面网站，包含前台商城与后台管理两大模块，共 25 个 HTML 页面（前台 15 页、后台 10 页）。

系统主要实现了以下功能：

- **前台**：首页、合作果园、果园详情与采摘预约、鲜果商城、产品详情、购物车、结算、下单成功、果业资讯、资讯详情、关于我们、联系我们、登录注册、个人中心；
- **后台**：管理员登录、数据看板、订单管理、产品管理、果园管理、采摘预约、资讯管理、用户管理、留言管理、系统设置；
- **业务闭环**：浏览商品 → 加入购物车 → 登录 → 结算下单 → 后台发货 → 用户确认收货；浏览果园 → 提交预约 → 后台确认；提交留言 → 后台回复；
- **数据能力**：localStorage 持久化、库存扣减与恢复、订单状态时间线、经营数据统计、Canvas 图表、JSON 导入导出、演示数据重置；
- **工程配套**：Node.js 零依赖静态服务器、一键启动脚本、MySQL 8.0 建表脚本、Playwright 自动化测试、完整毕业设计文档和答辩材料。

## 2 主要工作与收获

### 2.1 需求分析：从“想做什么”到“该做什么”

项目初期，我对“果园管理系统”的理解停留在“把果园信息放到网上”。通过调研和教师指导，我逐渐意识到，真正需要解决的不是“展示”，而是“信息分散、订单难管、客户难留”的问题。最终我把功能收敛为五类场景：果园展示、产品销售、订单履约、采摘预约、客户沟通，并围绕它们设计页面和数据结构。

这个过程让我体会到，需求分析不是把功能列得越多越好，而是明确“谁在什么场景下解决什么问题”。例如，最初我想做“农事记录、气象监测、物流跟踪”等复杂功能，但这些功能既缺少真实数据，也会稀释主流程。最终我选择把核心闭环做完整，把扩展点写进后续展望，这更符合毕业设计的时间和答辩要求。

### 2.2 系统设计：分层让代码更可控

系统采用“表示层—公共 UI 层—业务逻辑层—数据访问层—存储层”的分层思路。页面只负责结构和交互，所有数据读写集中在 `store.js`，页头页脚、Toast、Modal、图表等公共组件集中在 `ui.js`，前台和后台分别由 `front.js`、`admin.js` 组织页面逻辑。

这种分层带来的好处在后期非常明显：当需要修复“确认弹窗总是返回取消”的问题时，只需要改 `ui.js` 一处，所有删除、取消订单、停用用户等操作同时恢复；当需要把 localStorage 换成 MySQL 时，理论上只需要替换 `store.js` 的读写实现，页面层无需大改。

### 2.3 前端实现：在原生技术里做“完整产品”

为了满足“多个 HTML 文件、VS Code 可直接编辑”的要求，我没有使用 Vue/React，而是用原生 HTML、CSS 和 ES6 完成。实现过程中重点解决了以下问题：

- **公共结构复用**：用 JavaScript 渲染页头、页脚、移动菜单和用户菜单，避免 15 个页面重复维护；
- **视觉统一**：用 CSS 变量管理颜色、圆角、阴影和字体，用 Grid/Flex 完成响应式布局；
- **交互反馈**：Toast、Modal、Confirm、空状态、按钮禁用、错误提示，让用户知道“发生了什么”；
- **数据可视化**：用 Canvas 2D 手写折线图和环形图，处理高分屏缩放和窗口重绘；
- **移动端适配**：四级断点、抽屉导航、表格横向滚动、单列表单；
- **可访问性**：语义化标签、表单 label、aria-label、键盘焦点样式、减少动效偏好。

### 2.4 数据设计：让页面背后的数据“站得住”

数据层设计了用户、果园、产品、订单、订单明细、订单日志、资讯、留言、预约、配置等实体。为了保证历史订单不受产品改价影响，订单明细保存商品名称、单价、规格、图片快照；为了支持售后追溯，订单保存状态时间线；为了后续迁移，localStorage 字段与 MySQL 表字段尽量一一对应，并编写了完整的 `schema.sql`。

在库存处理上，我坚持“先校验、后扣减、取消恢复”的原则：下单前逐项检查库存，校验通过后统一扣减；取消待付款/待发货订单时恢复库存和销量，并记录日志。虽然 localStorage 没有事务，但通过顺序控制和按钮禁用，演示环境下可以保证数据一致。

### 2.5 测试与修复：从“能跑”到“敢演示”

项目后期，我编写了三套 Playwright 端到端测试，覆盖前台、后台、核心业务流和安全场景，共 65 项检查。测试过程中发现了多个问题，其中最有价值的是：

1. **确认弹窗逻辑错误**：`modal.close()` 触发 `onClose` 先把 Promise 置为 `false`，导致“确定”按钮实际返回取消，删除、取消订单、停用用户全部失效。修复方式是增加 `settled` 标志，先结算 Promise 再关闭弹窗。
2. **预约日期时区偏移**：用 `toISOString()` 取日期在东八区可能偏移一天，导致演示数据与测试预约冲突。修复方式是使用本地年月日拼接。
3. **个人中心用户名不显示**：对 disabled input 使用 `textContent` 无效，改为设置 `value`。
4. **后台筛选框换行**：全局 `.select { width:100% }` 影响表格筛选，改为 `width:auto`。

这些问题让我认识到，页面“看起来能点”不等于“逻辑正确”，只有把主流程走通、把边界情况测到，系统才真正可演示。修复后重新执行全部测试，65 项全部通过。

## 3 项目难点与解决方法

### 3.1 多页面结构下的状态共享

多页面每次跳转都会重新加载 JavaScript，登录状态、购物车、筛选条件无法像单页应用那样保存在内存中。解决方法是把会话和业务数据统一放入 localStorage，并在每个页面加载时由 `DB.init()` 恢复；购物车按用户隔离，登录时合并游客购物车。

### 3.2 订单与库存的一致性

下单涉及“校验库存—生成订单—扣减库存—增加销量—清空购物车”多个步骤，任何一步失败都可能造成数据不一致。解决方法是将这些步骤集中在 `DB.createOrder()` 中顺序执行，先完成全部校验再写入；取消订单时按明细恢复库存，并记录状态日志。

### 3.3 无框架条件下的组件复用

没有 Vue/React 的组件机制，页头页脚、弹窗、Toast 很容易重复。解决方法是用模板字符串封装 `headerHTML()`、`footerHTML()`、`modal()`、`toast()` 等函数，页面只保留占位节点，脚本加载后统一渲染。这样既保留了多页面的可读性，又减少了重复代码。

### 3.4 演示环境与生产环境的差距

毕业设计需要“打开就能演示”，但真实系统需要服务端、数据库、支付和物流。我的处理方式是：演示版用 localStorage 保证零配置运行，同时提供 MySQL 建表脚本和迁移说明，在文档中明确两者的差异。这样既不牺牲演示效果，也能在答辩中说明系统的工程化考虑。

## 4 不足与改进方向

### 4.1 不足

1. **数据存储受限**：localStorage 容量有限，无法支持多用户并发和跨设备同步；
2. **安全性不足**：演示版密码明文存储，缺少服务端鉴权、CSRF、防暴力破解和审计日志；
3. **业务深度有限**：未实现农事记录、批次溯源、物流跟踪、真实支付、图片上传等能力；
4. **兼容性测试不完整**：主要在 Edge 上测试，未对 Firefox、Safari 做完整回归；
5. **内容与数据真实性**：果园、产品、资讯为演示数据，未接入真实合作社业务。

### 4.2 改进方向

1. 使用 Spring Boot / Node.js + MySQL 重构服务端，补全事务、鉴权和接口文档；
2. 增加农事记录、投入品管理、采摘批次和“一物一码”溯源；
3. 接入微信支付/支付宝沙箱、物流查询、短信验证和对象存储；
4. 增加数据看板的更多维度（复购率、客单价、产地分布、季节趋势）；
5. 引入 Vue/React 或 Web Components，提升组件复用和交互体验；
6. 增加无障碍扫描、多浏览器云测试和持续集成；
7. 与真实果园合作，用真实数据验证产品分类、价格和履约流程。

## 5 答辩准备与心得体会

为了现场演示，我准备了三条主线：

1. **前台下单线**：首页 → 商城 → 加入购物车 → 登录 → 结算 → 下单成功；
2. **后台履约线**：管理员登录 → 数据看板 → 订单管理 → 发货 → 用户确认收货；
3. **特色功能线**：果园详情 → 采摘预约 → 后台确认；联系留言 → 后台回复。

在答辩讲解中，我会重点说明“为什么这样设计”，而不只是“有哪些页面”：为什么选择多页面、为什么用 localStorage、数据层如何封装、订单状态如何流转、库存如何保证一致、测试发现了什么问题。这些问题比单纯罗列功能更能体现专业能力。

通过这次毕业设计，我最大的收获不是学会了某个 API，而是完整经历了一个软件项目从需求到交付的过程：如何取舍功能、如何设计数据、如何组织代码、如何测试、如何写文档、如何向别人讲清楚。我也更深刻地体会到，技术的价值在于解决真实问题——哪怕只是帮助一座小果园把订单记得更清楚，也是有意义的事情。

## 6 结语

“武陵山区果园管理系统”还有很多可以完善的地方，但它已经具备了完整的前后台结构、可运行的核心业务、可追溯的数据设计和可复现的测试过程。感谢指导教师在选题、结构和文档上的指导，感谢参与调研和试用的人。未来如果有机会，我希望把它真正部署到一座果园里，让代码接受真实业务的检验。
