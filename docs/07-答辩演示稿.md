## 三、讲解逐字稿

### 1. 开场（约 40 秒）

各位老师好，我是计算机应用技术专业的______，我的毕业设计题目是《武陵山区果园管理系统的设计与实现》。本项目是一个可以直接在浏览器中运行的多页面网站，包含前台商城和后台管理两个模块，主要解决武陵山区中小果园“信息分散、订单难管、客户难留”的问题。

下面我从选题背景、系统设计、功能演示和测试情况四个方面进行汇报。

### 2. 选题背景（约 60 秒）

武陵山区横跨湘、鄂、渝、黔四省市，海拔高、云雾多、昼夜温差大，适合猕猴桃、柑橘、梨、李、莓茶等特色农产品生长。但在调研中我发现，很多中小果园仍然用纸笔、微信群和 Excel 管理业务：果园档案散落、库存更新滞后、订单靠手工登记、采摘预约靠口头确认、客户咨询没人沉淀。

大型农业系统功能复杂、成本高，不适合这些小果园。因此我想做一个“轻量、够用、打开就能演示”的系统，把果园展示、产品销售、订单履约、采摘预约和客户沟通整合在一起。这就是本课题的出发点。

### 3. 需求与目标（约 60 秒）

系统有三类用户：游客、普通用户、管理员。游客可以浏览、搜索、加购；普通用户可以下单、预约、留言、查看自己的订单；管理员负责产品、果园、订单、资讯、用户、留言和预约的处理。

我把需求收敛为两条核心闭环：第一条是“浏览商品—加购—登录—结算—后台发货—确认收货”；第二条是“浏览果园—提交预约—后台确认”。围绕这两条闭环，设计了前台 15 个页面、后台 10 个页面。这样既保证功能完整，也避免做成一个“什么都有、什么都不深”的系统。

### 4. 系统架构（约 80 秒）

系统采用 B/S 架构下的多页面应用。最上面是表示层，前台和后台的 HTML 页面负责结构和样式；中间是公共 UI 层和业务逻辑层，`ui.js` 负责页头页脚、Toast、弹窗、图表，`front.js` 和 `admin.js` 负责页面路由和业务；下面是统一的数据访问层 `store.js`，所有实体的读写、库存校验、订单状态、统计聚合都在这里；最底层是 localStorage，演示版用它模拟数据库。

这样分层的好处是：页面不直接操作 localStorage，后续要把数据层换成 MySQL 或 REST API，只需要改 `store.js`，页面层基本不用动。数据库方面，我另外编写了 MySQL 8.0 的建表脚本，包含用户、果园、产品、订单、订单明细、订单日志、资讯、留言、预约、配置 10 张表，字段和演示版实体一一对应。

技术选型上，我使用原生 HTML5、CSS3、ES6、Canvas 2D、localStorage，没有使用 Vue/React，也没有依赖 CDN。原因有两个：一是题目要求由多个 HTML 文件组成、用 VS Code 直接编辑；二是希望把教学重点放在原生 Web 技术、数据建模和业务逻辑上，而不是框架配置。

### 5. 功能演示（约 3—4 分钟）

**第一步：前台首页。** 展示品牌主视觉、合作果园、当季产品、果园故事和资讯。导航可以进入果园、商城、资讯、关于和联系页面，购物车角标会实时变化。

**第二步：商城与加购。** 进入鲜果商城，可以按鲜果、山货、茶叶筛选，也可以搜索、按价格或销量排序。点击产品卡的加号加入购物车，右上角角标加一。

**第三步：登录与结算。** 进入购物车，调整数量，点击去结算。未登录会跳转登录页，登录后回到结算页。结算页自动带出姓名、手机号和地址，计算商品金额和运费，提交后生成订单号。

**第四步：后台处理。** 打开后台，用管理员账号登录。数据看板可以看到销售额、订单量、待发货、库存预警，以及近 6 个月趋势图、品类占比、最新订单。进入订单管理，找到刚才的订单，点击发货，状态变成已发货。

**第五步：用户确认。** 回到个人中心，订单状态已经是已发货，点击确认收货，订单完成。整个过程库存、销量、状态时间线都会同步变化。

**第六步（可选）：采摘预约。** 进入果园详情，填写日期和人数提交预约；后台预约管理确认后，用户可以在个人中心看到状态。

### 6. 数据库与关键技术（约 60 秒）

数据库设计的核心是“订单快照”和“状态日志”。订单明细保存下单时的商品名称、单价、规格和图片，这样产品后续改价或删除，历史订单仍然准确；订单日志记录每次状态变化，支撑个人中心和后台的时间线。

库存一致性方面，下单前逐项校验库存，校验通过后统一扣减，取消订单时按明细恢复。演示版 localStorage 没有事务，所以我用“先校验、后写入”和提交按钮禁用来降低风险；生产环境会在 MySQL 中用事务和行锁实现。

另外两个技术点：一是用 Canvas 2D 手写折线图和环形图，处理了高分屏缩放和窗口重绘；二是用 CSS 变量、Grid/Flex 和四级断点做响应式，桌面和手机都能用。

### 7. 测试情况（约 60 秒）

我编写了三套 Playwright 端到端测试，覆盖前台、后台、核心业务流和安全场景，共 65 项检查，最终全部通过。测试过程中发现并修复了 7 个缺陷，其中最严重的是确认弹窗的 Promise 结算顺序问题：`modal.close()` 先触发 `onClose` 把结果置为 false，导致删除、取消订单、停用用户等操作全部失效。我通过增加 `settled` 标志，先结算 Promise 再关闭弹窗，修复后重新执行全部用例。

此外还修复了预约日期时区偏移、个人中心用户名不显示、后台筛选框换行、订单总额未含运费、购物车重复绑定等问题。测试让我意识到，“页面能点”不等于“逻辑正确”，只有把主流程和边界情况都走一遍，系统才真正可演示。

### 8. 不足与展望（约 40 秒）

系统还有不足：演示版数据存在 localStorage，不能多用户并发和跨设备同步；密码是明文，缺少服务端鉴权；没有接入真实支付、物流和图片上传；农事记录、批次溯源等农业场景还可以继续深入。

后续我计划用 Spring Boot 或 Node.js + MySQL 重构服务端，补全事务和权限；增加农事记录、采摘批次和“一物一码”溯源；接入支付沙箱和物流查询；如果条件允许，和真实果园合作，用真实数据验证。

### 9. 结语（约 20 秒）

这次毕业设计让我完整经历了一个项目从需求、设计、开发到测试和文档的过程。最大的收获不是学会了某个 API，而是学会了如何取舍功能、如何设计数据、如何验证系统，以及如何把一件事讲清楚。我的汇报完毕，请各位老师批评指正，谢谢！

## 五、常见问题与回答

### Q1：为什么不用 Vue 或 React？

**答**：题目要求由多个 HTML 文件组成、用 VS Code 直接编辑，多页面原生实现更符合要求。另一方面，我希望把重点放在原生 Web 技术、数据建模和业务逻辑上。项目里仍然做了组件化：页头页脚、Toast、Modal、图表都封装在 `ui.js`，页面只保留占位节点。如果后续要升级，可以把这些组件迁移到 Vue/React。

### Q2：localStorage 算数据库吗？为什么不用 MySQL？

**答**：localStorage 不是数据库，它是浏览器提供的键值存储。演示版用它，是为了零配置、打开就能运行，方便答辩现场展示。它不支持事务、并发和复杂查询，所以我在文档里明确它是“演示数据层”，另外编写了 MySQL 8.0 的建表脚本和迁移说明。生产环境会把 `store.js` 的读写替换为服务端 API，用 MySQL 存数据。

### Q3：数据丢了怎么办？

**答**：演示版提供两个保护：一是后台“导出数据备份”可以下载 JSON；二是“恢复演示数据”可以一键回到初始状态。正式环境会每日备份数据库，并使用 binlog 做增量恢复。

### Q4：如何保证库存一致性？两个人同时下单怎么办？

**答**：演示版在下单前逐项校验库存，校验通过后统一扣减；取消订单时按明细恢复；提交按钮会立即禁用，防止重复点击。localStorage 是单浏览器、单线程的，不存在真正的并发。生产环境会把下单放在 MySQL 事务里，使用 `SELECT ... FOR UPDATE` 锁定库存行，再扣减、写订单和日志，保证并发安全。

### Q5：订单状态是怎么流转的？

**答**：订单有五个状态：待付款、待发货、已发货、已完成、已取消。正常流程是待付款 → 待发货 → 已发货 → 已完成；待付款和待发货可以取消，取消后恢复库存。后台负责发货和完成，用户可以确认收货和取消待发货订单。每次变化都会写入 `timeline`，个人中心和后台都能看到时间线。

### Q6：密码为什么是明文？安全吗？

**答**：演示版为了让学生能直接看到初始账号，密码以明文保存在 localStorage，这确实不适合生产。文档里已经注明：生产环境必须使用 BCrypt/Argon2 哈希，服务端鉴权，HTTPS，登录限流和审计日志。系统里没有存储任何真实支付信息。

### Q7：系统的架构讲一下？

**答**：B/S 架构、多页面应用，分五层：表示层是 25 个 HTML 页面；公共 UI 层是 `ui.js`；业务逻辑层是 `front.js` 和 `admin.js`；数据访问层是 `store.js`；存储层是 localStorage，生产可换 MySQL。页面不直接读写 localStorage，所有实体操作都走数据层，这样耦合低、可测试、可迁移。

### Q8：数据库设计符合三范式吗？

**答**：核心表基本满足第三范式，比如用户、果园、产品、订单分开，订单明细通过 `order_id` 关联。但订单明细有意保留商品名称、单价、规格、图片等快照字段，这是反范式的设计，目的是保证历史订单不受产品改价或删除影响。实际项目中，这种“适度冗余”是合理的。

### Q9：测试是怎么做的？

**答**：分三层：第一层是 `node --check` 语法检查和 HTML 链接扫描；第二层是 Playwright 端到端测试，模拟真实点击、输入和页面跳转；第三层是手工检查响应式、图片加载、移动端布局。三套自动化脚本共 65 项检查，覆盖登录、购物车、下单、取消、预约、留言、后台 CRUD、权限控制和 XSS 防护，最终全部通过。

### Q10：开发中最难的地方是什么？

**答**：最难的是多页面下的状态共享和库存一致性。多页面每次跳转都会重新加载脚本，登录、购物车、筛选条件不能放在内存里；我的解决办法是统一放 localStorage，按用户隔离购物车，登录时合并游客购物车。库存方面要把校验、扣减、恢复、日志串起来，任何一步顺序错了都会出问题。

### Q11：这个项目有什么创新或特色？

**答**：我不敢说有多大创新，但有几个特点：一是把“果园档案 + 电商 + 预约 + 留言 + 资讯”整合在一个轻量系统里，贴近中小果园的真实场景；二是数据层做了统一封装，localStorage 和 MySQL 字段对应，具备迁移思路；三是用原生 Canvas 手写图表、零依赖、离线可演示；四是写了 65 项自动化测试，不是只靠手工点页面。

### Q12：如果真正上线，需要改什么？

**答**：需要做五件事：第一，服务端和 MySQL，补事务、鉴权和接口；第二，密码哈希、HTTPS、CSRF、限流和审计；第三，接入微信支付/支付宝、物流查询、短信和对象存储；第四，补充农事记录、批次溯源、图片上传；第五，做多浏览器兼容、性能优化和备份监控。

### Q13：为什么前台和后台要分开？

**答**：前台面向消费者，重点是浏览、信任和下单体验；后台面向管理员，重点是表格、筛选、批量处理和状态流转。两类用户的目标和交互差异很大，分开可以让界面更专注，也方便做权限控制。技术上它们共享同一套数据层和 UI 基础组件，不是两套独立系统。

### Q14：为什么页面这么多？怎么保证一致性？

**答**：多页面是题目要求，也符合传统网站的结构。为了保证一致性，我把页头、页脚、移动菜单、用户菜单、Toast、Modal 都封装在 `ui.js`，每个页面只保留占位节点，加载后统一渲染；颜色、圆角、阴影用 CSS 变量统一；数据都走 `store.js`。所以新增页面只需要引入三个脚本和两个样式，不需要复制大量代码。

### Q15：图表是怎么画的？

**答**：用 Canvas 2D 原生绘制。折线图先计算坐标轴、网格、数据点，再画渐变面积、折线和圆点；环形图用 `arc` 画扇形，中间留空显示总额。为了高分屏清晰，根据 `devicePixelRatio` 放大画布；窗口大小变化时用防抖重绘。

### Q16：如何防止用户重复下单？

**答**：前端在提交时立即禁用按钮并改文案，防止连续点击；数据层生成唯一订单号；下单后清空购物车。生产环境还会加幂等 token、服务端订单号唯一索引和接口限流。

### Q17：预约日期为什么不能选今天？

**答**：因为果园需要提前准备接待，系统默认从明天开始可选，建议至少提前 3 天预约。这个规则在表单 `min` 和数据层都有校验，避免用户绕过页面直接提交。

### Q18：项目还有哪些不足？

**答**：主要是四点：localStorage 不能多用户并发；密码明文、缺少服务端安全；没有真实支付、物流和图片上传；农事记录、批次溯源等农业深度功能还不够。这些我都写进了总结和后续展望，不是回避问题。

## 六、答辩应急方案

| 情况 | 处理方式 |
|---|---|
| 服务器启动失败 | 检查 Node 是否安装；改用 VS Code Live Server；或直接打开备份的静态页面（部分功能受限） |
| 端口被占用 | `set PORT=8081 && node server.js`，改访问 8081 |
| 数据被改乱 | 后台“系统设置”→“恢复演示数据”，重新登录 |
| 图片不显示 | 确认通过 `http://localhost` 访问，不要直接双击 HTML |
| 后台登录失败 | 确认使用 `admin / admin123`，检查是否被普通用户会话覆盖 |
| 投影分辨率低 | 浏览器缩放 90%，使用 1440×900 窗口，关闭开发者工具 |
| 现场网络不可用 | 系统不依赖外网，所有资源本地加载；提前准备截图和录屏 |
| 时间不够 | 跳过资讯、关于、设置，只演示“商城下单 + 后台发货 + 用户确认”主线 |
